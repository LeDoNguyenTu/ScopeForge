# Phase 6D Dedicated Network Worker Design

Status: design only. No runtime implementation or enablement is authorized by this document alone.

## Purpose

Phase 6D moves the already-approved passive runtime observation and bounded active CORS validation execution paths behind dedicated worker classes without widening their authority.

The design preserves the existing Phase 4 security contracts while separating network-capable execution from the Vercel control plane. It deliberately does not create a generic network executor.

## Goals

1. Preserve the exact current authorization requirements for passive runtime observation and active CORS validation.
2. Preserve immediate execution-time reauthorization against the current asset state.
3. Preserve DNS and public-IP safety, HTTPS-only transport, hostname/TLS binding, redirect validation, fixed request shapes, fixed budgets, bounded observations, cancellation, deterministic rule evaluation, and trusted persistence.
4. Move network activity into dedicated worker classes with narrower credentials and operational isolation.
5. Keep passive and active runtime authority independently deployable and independently disabled.
6. Provide clear backpressure, timeout, cancellation, failure, audit, and fleet-health semantics.
7. Make any future authority expansion require a new execution class, threat model, design approval, and tests.

## Non-goals

Phase 6D does not add:

- generic URL fetching
- arbitrary HTTP methods
- caller-supplied headers
- caller-supplied request bodies
- authentication replay
- cookie forwarding
- credentialed crawling
- POST/PUT/PATCH/DELETE requests
- browser automation
- path discovery
- content fuzzing
- port scanning
- arbitrary redirect following
- arbitrary DNS resolution APIs
- generic proxying
- exploit execution
- unrestricted outbound network access
- reuse of the Phase 6B GitHub archive network policy
- service-role credentials inside network workers

Any such capability requires a separate design boundary.

## Existing guarantees that must not regress

### Passive runtime observation

The current passive path supports verified web and API assets and reauthorizes the queued job against the current asset immediately before network execution.

The current maximum budget is:

- maxRequests: 4
- maxRedirects: 3
- perRequestTimeoutMs: 5000
- totalTimeoutMs: 15000
- maxObservationBytes: 65536

Each request is a fixed HTTPS GET generated by ScopeForge. Redirects are individually evaluated against the authorized target policy before following. The observer checks cancellation before requests, after responses, and around redirect transitions.

### Active CORS validation

The current active path requires:

- authenticated actor
- workspace owner or admin role
- explicit active-validation consent for the run
- verified web or API asset
- unchanged canonical target
- unchanged asset kind
- unchanged verification timestamp
- exact approved CORS profile ID and version
- exact approved budget

The current maximum and required budget is:

- maxRequests: 1
- maxRedirects: 0
- perRequestTimeoutMs: 5000
- totalTimeoutMs: 10000
- maxObservationBytes: 32768

The request is exactly one unauthenticated HTTPS GET to port 443 with:

- fixed ScopeForge active-runtime user agent
- fixed synthetic Origin
- fixed Accept header
- no caller headers
- no credentials
- no body
- no query expansion
- no redirect following

These guarantees are part of Phase 6D acceptance criteria, not implementation suggestions.

## Threat model

### Protected assets

Phase 6D protects:

- third-party and customer-controlled runtime targets
- workspace authorization boundaries
- verification state and target ownership state
- active-validation consent state
- internal/private network ranges
- worker credentials and broker authority
- database mutation authority
- runtime observations and finding evidence
- target response privacy
- operational availability of the worker fleet

### Adversaries and failure sources

The design assumes possible:

- malicious authenticated workspace users
- compromised or hostile verified targets
- DNS rebinding attempts
- redirect chains attempting to reach private/internal addresses
- malformed TLS/HTTP responses
- oversized or intentionally slow responses
- cancellation races
- stale queued authorization snapshots
- replayed worker contracts
- compromised worker process
- accidental operator misconfiguration
- malformed terminal worker output
- queue flooding and noisy-neighbor behavior
- Vercel/control-plane retry behavior

### Primary abuse cases

The implementation must prevent:

1. Turning ScopeForge into an SSRF service.
2. Using a worker lease to contact a target other than the reauthorized asset.
3. Reusing active authorization for a different asset or later changed asset state.
4. Expanding one approved active CORS request into arbitrary HTTP traffic.
5. Following a passive redirect into a private or otherwise unauthorized destination.
6. Exfiltrating response bodies, cookies, authorization data, or arbitrary remote content through worker results.
7. Publishing a result after authoritative cancellation.
8. Replaying a completed or expired worker lease.
9. Letting a network worker mutate the hosted finding ledger directly.
10. Letting the Phase 6B GitHub networking policy become a generic egress primitive.

## Architectural decision

Phase 6D introduces two independent worker execution classes:

- `passive_runtime_observation_v1`
- `active_cors_validation_v1`

It does not introduce `network_v1`, `http_request_v1`, `fetch_url_v1`, or any equivalent generic class.

Each class has its own input schema, network policy, maximum budget, result schema, failure codes, capability gate, and acceptance tests.

The two classes may share low-level implementation helpers only where those helpers do not carry policy authority. Shared helpers may implement primitives such as IP classification, TLS connection pinning, byte counting, timeout handling, or redaction. Policy decisions remain in class-specific code.

## High-level execution flow

1. User requests an existing passive or active operation through the current application action/API.
2. The Vercel control plane applies the existing enqueue authorization rules.
3. The existing domain job is created with its immutable authorization snapshot.
4. If the corresponding hosted worker capability is disabled, execution fails closed and no network worker task is enqueued.
5. If enabled, the control plane creates a closed worker task referencing the domain job identity, not an arbitrary caller-supplied URL.
6. A worker claims the task using the existing lease model.
7. Before any network activity, the worker requests a lease-bound preparation document from the trusted control plane.
8. The control plane loads the current domain job and asset, performs immediate reauthorization using the existing Phase 4 authorization functions, validates cancellation and job state, and returns a closed execution profile.
9. The worker validates the execution profile against its compile-time class schema and its own hard maximums.
10. The dedicated executor performs the allowed network activity using pinned HTTPS safety primitives.
11. The worker emits only the normalized class-specific terminal result.
12. The control plane rechecks attempt identity, lease validity, cancellation state, result schema, result budgets, and domain job state.
13. The existing deterministic rules and trusted persistence path transform accepted observations into evidence/findings and domain lifecycle updates.
14. Cancellation or validation failure wins over a late worker success.

## Control-plane preparation endpoint

The preparation endpoint is a trusted internal worker endpoint. It is not callable as a generic browser API.

The worker supplies only:

- worker task ID
- attempt ID
- execution class
- lease credential
- domain job reference already bound to the worker task

The worker does not supply a URL, HTTP method, headers, body, redirect policy, or authorization snapshot for the control plane to accept.

The control plane reconstructs authority from trusted hosted state.

Preparation must:

1. Authenticate the lease and worker class.
2. Verify the task and attempt are current.
3. Load the referenced domain job.
4. Load the current workspace asset.
5. Execute the existing passive or active reauthorization function.
6. Reject requested/authoritative cancellation before networking.
7. Reject terminal or otherwise non-executable domain job state.
8. Enforce the class capability gate.
9. Return a short-lived, lease-bound, single-job execution profile.

The preparation response must expire no later than the worker attempt deadline and must be unusable by a different task, attempt, or execution class.

## Closed execution profiles

### Passive profile

`passive_runtime_observation_v1` preparation returns only the data required to execute the existing passive observer contract:

- asset reference
- asset kind
- canonical HTTPS URL
- authorized hostname
- exact persisted runtime observation budget
- attempt deadline
- execution profile version

The budget must pass the existing runtime-observation validation and must not exceed the hard Phase 4 maximums.

### Active CORS profile

`active_cors_validation_v1` preparation returns only:

- asset reference
- asset kind
- canonical HTTPS URL
- authorized hostname
- fixed CORS profile ID/version
- exact active-validation budget
- authorization-granted timestamp for audit/provenance
- attempt deadline
- execution profile version

The worker does not receive actor credentials or permission to modify the request profile.

## Network policy

### Common transport requirements

Both network worker classes must use the existing pinned HTTPS safety model or a behaviorally equivalent implementation covered by the same tests.

For every network destination:

1. Parse and validate the URL.
2. Require HTTPS.
3. Reject URL credentials.
4. Resolve DNS under bounded timeout and answer-count limits.
5. Reject private, loopback, link-local, multicast, reserved, unspecified, carrier-grade NAT, documentation-only where policy requires, and other non-public destinations according to the established runtime IP policy.
6. Select an approved resolved public IP.
7. Connect to that IP while preserving the authorized hostname for TLS SNI and certificate verification.
8. Reject certificate/hostname failures.
9. Do not trust connection-time DNS to choose a different destination.
10. Apply request and response byte/time ceilings.

DNS and connection handling must not expose a generic helper callable with arbitrary caller input from outside the class executor.

### Passive redirects

For `passive_runtime_observation_v1`:

- redirects are inspected only after the current response is normalized
- each redirect is validated using the existing passive redirect policy
- the redirect budget remains at most 3
- total requests remain at most 4
- every allowed redirect destination undergoes fresh DNS/IP safety checks before connection
- disallowed redirects are recorded only as bounded/redacted redirect observations
- no redirect is followed merely because it is same-origin according to the remote server

### Active CORS

For `active_cors_validation_v1`:

- exactly one request is permitted
- redirects are never followed
- HTTPS port must be 443
- method is fixed GET
- headers are fixed by the approved CORS request plan
- request body is absent
- credentials are absent
- response body is not captured

## Worker credentials and authority

Network workers must not receive:

- Supabase service-role key
- browser JWTs
- user refresh/access tokens
- workspace member credentials
- arbitrary database credentials
- R2 write authority unless a future separately approved execution class explicitly needs it
- GitHub archive acquisition credentials/policies

A worker receives only the existing scoped worker credential/lease mechanism plus the short-lived preparation profile for the claimed attempt.

The worker cannot publish directly to domain tables.

## Result privacy

Worker terminal results are normalized observations only.

They must not contain:

- full response bodies
- request bodies
- cookies
- Set-Cookie values
- Authorization values
- Proxy-Authorization values
- arbitrary caller headers
- TLS private material
- full DNS resolver transcripts
- raw secrets discovered in page content
- unbounded header sets
- uncontrolled error strings from remote content

Passive observations use the existing redaction and observation builders. Active CORS uses the existing bounded CORS observation builder.

Terminal envelope size is bounded independently from the domain observation budget.

## Deterministic persistence

Workers do not create findings.

On an accepted worker success:

- passive observations are evaluated by the existing runtime rule engine
- active CORS observation is evaluated by the existing CORS policy rule engine
- evidence and finding mapping remain deterministic
- canonical persistence stays in the trusted control plane/repository layer
- existing job audit/lifecycle events remain authoritative

A malformed or over-budget terminal result fails the worker attempt and does not partially persist observations or findings.

## Cancellation semantics

Cancellation wins over completion.

Required cancellation checks occur:

- before worker preparation
- during preparation
- immediately before first network activity
- between passive requests
- after each network response
- before following a passive redirect
- before terminal publication
- again in the control plane before accepting terminal success

If cancellation becomes authoritative at any point before successful trusted publication, the domain operation resolves as cancelled and worker observations are discarded for finding publication.

The active request may already have reached the remote target when cancellation arrives. Cancellation cannot undo completed remote I/O, but it must stop further processing/publication and active validation has no second request to send.

## Budgets and worker profiles

Worker-supervisor resource ceilings are separate from network semantic budgets.

Recommended initial supervisor ceilings:

### `passive_runtime_observation_v1`

- maxWallTimeMs: 30000
- maxCpuTimeMs: 15000
- maxMemoryBytes: 268435456
- maxProcesses: 1
- maxInputFiles: 0
- maxInputBytes: 65536
- maxScratchBytes: 16777216
- maxOutputBytes: 131072

### `active_cors_validation_v1`

- maxWallTimeMs: 20000
- maxCpuTimeMs: 10000
- maxMemoryBytes: 268435456
- maxProcesses: 1
- maxInputFiles: 0
- maxInputBytes: 32768
- maxScratchBytes: 8388608
- maxOutputBytes: 65536

These supervisor ceilings provide execution overhead around the stricter Phase 4 network budgets. They do not authorize more requests, redirects, observation bytes, or target scope.

The implementation may choose tighter supervisor ceilings after measurement, but it may not exceed these values without a design amendment.

## Queueing and backpressure

Passive and active classes have independent concurrency and queue controls.

The broker must support:

- per-class availability
- per-class maximum concurrent attempts
- workspace-level quota checks before enqueue
- bounded retry count for infrastructure failures
- no retry for authorization/policy failures
- attempt deadlines
- lease expiry and lost-worker recovery

Active CORS should have the stricter concurrency/backpressure policy because it represents explicitly authorized active traffic.

A retry must never bypass reauthorization. Every attempt receives a fresh preparation decision.

## Failure taxonomy

Worker-level failures should be closed and machine-readable. Recommended new failure groups include:

### Common

- `RUNTIME_WORKER_AUTHORIZATION_FAILED`
- `RUNTIME_WORKER_CANCELLED`
- `RUNTIME_WORKER_NETWORK_POLICY_FAILED`
- `RUNTIME_WORKER_BUDGET_EXCEEDED`
- `RUNTIME_WORKER_OUTPUT_INVALID`
- `RUNTIME_WORKER_EXECUTION_FAILED`

### Passive-specific

- `PASSIVE_RUNTIME_REQUEST_TIMEOUT`
- `PASSIVE_RUNTIME_TOTAL_TIMEOUT`
- `PASSIVE_RUNTIME_NETWORK_ERROR`
- `PASSIVE_RUNTIME_OBSERVATION_BUDGET`

### Active-specific

- `ACTIVE_CORS_REQUEST_TIMEOUT`
- `ACTIVE_CORS_TOTAL_TIMEOUT`
- `ACTIVE_CORS_NETWORK_ERROR`
- `ACTIVE_CORS_OBSERVATION_BUDGET`

Control-plane mapping may translate these into the existing safe domain failure codes where compatibility requires it. Raw remote error strings must not become public failure messages.

## Capability gates

Two independent server-controlled capability gates are required and default false:

- `HOSTED_PASSIVE_RUNTIME_WORKER_ENABLED=false`
- `HOSTED_ACTIVE_CORS_WORKER_ENABLED=false`

Rules:

1. A false gate prevents enqueueing work that requires that runtime.
2. Enabling passive does not enable active.
3. Enabling active does not enable passive.
4. These flags do not modify Phase 6B/6C repository runtime gates.
5. No UI may claim hosted runtime worker availability while its corresponding gate is false.
6. The active gate must not be enabled until the passive/shared network primitives have passed the required network-policy acceptance tests and the active class has separately passed its exact-one-request acceptance tests.

## Deployment topology

The recommended topology is a dedicated Linux worker service separate from Vercel.

It runs the existing worker broker/supervisor model with network-enabled executors only for the two approved classes.

Repository snapshot acquisition and repository scan workers remain separate execution authorities:

- Phase 6B GitHub acquisition keeps its GitHub-specific network class
- Phase 6C repository scanning remains zero-egress
- Phase 6D runtime workers use target-bound runtime network classes

The implementation must not combine all classes into a single unrestricted container profile merely for operational convenience.

## R2 and artifact storage

Phase 6D does not require Cloudflare R2 for runtime observations.

Normalized passive and CORS observations are small and already bounded for trusted database persistence. Introducing an object-store artifact path would add credentials, lifecycle, and privacy complexity without a current requirement.

If future runtime profiles need large artifacts, that requires a separate design amendment.

## Audit and observability

The trusted control plane remains responsible for domain audit events.

Operational worker telemetry may record:

- execution class
- task/attempt identifiers
- lease age
- queue wait duration
- wall/cpu/memory metrics
- request count
- redirect count where applicable
- normalized failure code
- cancellation timing category

Operational logs must not include full target response bodies, raw secrets, cookies, authorization headers, or worker lease credentials.

Fleet health should expose class availability and saturation without exposing target data.

## Migration strategy

Phase 6D should not replace the current execution path in one step.

Recommended sequence:

1. Add contracts, profiles, validators, and architecture guards with both gates false.
2. Add trusted preparation and terminal-publication paths with no production worker enabled.
3. Add passive worker executor and focused integration tests.
4. Perform Linux network-policy acceptance testing for passive class.
5. Enable passive only in a controlled environment and verify operational behavior.
6. Add active CORS worker executor using the same low-level transport primitives but its own class policy.
7. Perform exact-one-request active acceptance testing including cancellation and redirect rejection.
8. Enable active independently.
9. Remove direct Vercel execution only after the corresponding worker path has proven equivalent/fail-closed behavior and rollback remains available.

During migration, the system must never fall back from a disabled/failed worker class to a broader or less isolated network execution path automatically.

## Rollback

Rollback is capability-based, not authority-expanding.

If a worker class shows safety or reliability problems:

- set its hosted capability gate false
- stop new task creation
- cancel/expire outstanding attempts according to queue semantics
- preserve existing findings and audit history
- do not redirect those jobs to a generic Vercel fetch path

## Testing requirements

### Contract tests

Must prove:

- only the two new execution classes are accepted
- class/input mismatch is rejected
- budgets cannot exceed hard maxima
- extra fields that would widen HTTP authority are rejected
- attempt/task/class/lease binding is exact
- terminal results reject extra/unbounded raw response data

### Authorization tests

Must prove:

- passive execution cannot proceed after asset verification/target state changes
- active execution cannot proceed after authorization snapshot changes
- active requires owner/admin and explicit consent at enqueue
- every retry performs fresh preparation/reauthorization
- cancelled jobs never receive a usable preparation profile

### Network safety tests

Must cover:

- loopback IPv4/IPv6
- RFC1918/private ranges
- link-local
- multicast
- unspecified addresses
- IPv4-mapped IPv6 forms
- DNS rebinding/different resolution stages
- multiple DNS answers including unsafe answers
- TLS hostname mismatch
- redirects to private/unsafe destinations
- redirects exceeding passive limits
- active redirect response never followed
- port restrictions for active CORS

### Request-shape tests

Active CORS tests must independently observe the outgoing request and prove:

- exactly one request
- GET only
- port 443 only
- fixed synthetic Origin
- fixed user agent
- fixed Accept
- zero caller headers
- zero credentials
- zero body
- zero redirects followed

Passive tests must prove its fixed request profile and redirect policy remain equivalent to Phase 4.

### Cancellation tests

Must cover cancellation:

- before preparation
- after preparation before network
- while a passive request is in flight
- between passive requests
- after response before redirect
- after final response before publication
- after worker terminal success arrives but before trusted publication

Expected rule: cancellation wins whenever trusted publication has not completed.

### Privacy tests

Sentinel values in:

- response bodies
- Set-Cookie
- Authorization-like response text
- Location query strings
- error text

must not leak into terminal envelopes, public findings, or operational logs beyond the established redacted representation.

### Operational acceptance

Before either production gate becomes true, a real Linux environment must demonstrate:

- worker lease expiry/recovery
- process termination on supervisor wall timeout
- cancellation terminates or suppresses further execution/publication
- memory/process ceilings are enforced
- network policy blocks disallowed addresses even under DNS changes
- class saturation/backpressure works
- no service-role credential exists in worker environment
- no generic outbound execution class is available

## Architecture guards

Permanent tests or static guards must fail if future changes attempt to:

- add a generic URL/network worker class without an approved design
- pass service-role credentials into executors
- pass caller-controlled method/headers/body into active CORS
- reuse the GitHub acquisition network policy for runtime targets
- let network workers persist findings directly
- make repository scan workers network-enabled
- couple passive and active capability gates
- silently fall back to direct Vercel network execution when a worker runtime is disabled

## Acceptance criteria

Phase 6D implementation is complete only when:

1. The two closed execution classes exist with independent network policies and gates.
2. Existing Phase 4 authorization tests still pass unchanged in meaning.
3. Fresh execution-time reauthorization is proven for every worker attempt.
4. Passive behavior stays within 4 requests, 3 redirects, 15 seconds, and 64 KiB observations.
5. Active CORS stays exactly 1 GET, 0 redirects, 10 seconds, and 32 KiB observations with fixed headers and no credentials/body.
6. DNS/IP/TLS/redirect safety is enforced inside the worker network boundary.
7. Cancellation-wins races are covered through trusted publication.
8. Worker results are normalized and privacy-bounded.
9. Workers cannot directly mutate the canonical finding ledger.
10. Production enablement remains false until real Linux operational acceptance is recorded.
11. Passive and active can be enabled, disabled, and rolled back independently.
12. No generic network executor is introduced.

## Security decision record

The central design decision is that network capability is not a reusable permission. It is an implementation detail of a narrowly named, versioned execution class whose complete request authority is reviewable from its contract.

Phase 6D therefore accepts some duplication between passive and active worker policy code in exchange for preventing authority convergence. Shared transport primitives are acceptable; shared generic request authority is not.
